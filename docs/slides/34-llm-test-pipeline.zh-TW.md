# LLM 測試生成管線
### 讓 LLM 在寫測試上*變得可靠*

軟體測試視覺化系列 #34 · 進階測試
搭配工具：`/section-advanced`（[LLMPipelineExplorer](../../src/components/LLMPipelineExplorer.js)）

<!-- 基於 ACH 論文（Meta，arXiv 2501.12862）。本講論點：原始 LLM 不可靠；*包在它外面的管線*則不然。 -->

---

## 為什麼有這一講

- 「叫 LLM 寫測試」會產出*看起來*合理的測試 —— 卻常常什麼有用的東西都沒斷言。
- 一個通過卻什麼都不檢查的測試，**增加了覆蓋率、抓錯能力卻是零**（#33）。
- Meta 的 **ACH**（Automated Compliance Hardener，arXiv 2501.12862）透過把模型包進一條管線，讓 LLM 測試生成*變得可靠*。
- 管線的骨幹是**突變測試** —— #33 的那個客觀度量。

---

## 原始 LLM 的問題

對 LLM 下「替這個函式寫測試」的提示，你會得到：

- 能編譯、會通過的測試 —— 但斷言薄弱或同義反覆。
- 沒有任何客觀訊號顯示測試是否會*抓到*什麼。
- LLM 沒有基準真相；「看起來像測試」不等於「是好測試」。

ACH 的解法：給 LLM 一個**目標** —— 一個要抓的特定錯誤 —— 與一個**預言** —— 突變測試 —— 來驗證它做到了。

---

## 三階段管線

ACH 串接三個由 LLM 驅動的階段：

```
   ┌───────────┐   ┌──────────────┐   ┌──────────────┐
   │ 1 突變    │──▶│ 2 等價        │──▶│ 3 測試       │
   │   生成    │   │   過濾       │   │   生成       │
   └───────────┘   └──────────────┘   └──────────────┘
```

| 階段 | 它做什麼 |
| --- | --- |
| 1. 突變 | 在目標程式碼中生成候選錯誤（突變體） |
| 2. 等價 | 丟棄等價突變體（#32）—— 它們殺不死 |
| 3. 測試生成 | 為每個存活的突變體生成一個能**殺死**它的測試 |

---

## 第 3 階段內建一個預言

關鍵的設計點：第 3 階段的成功是**客觀可檢查的**。

- LLM 寫一個瞄準某個特定存活突變體的測試。
- 跑它：它在**原程式上通過**、且在**突變體上失敗**嗎？
- 若是 → 該測試可證明地抓到那個錯誤 —— **留下。**
- 若否 → 丟棄，或重新提示 LLM。

> LLM 提議；**突變測試裁決。** 沒有人需要逐一審判每個測試。

這就是為什麼管線可靠、而原始 LLM 不可靠。

---

## 為什麼突變測試是骨幹

每個管線階段都倚賴 #32–#33 的突變概念：

- 第 1 階段*就是*突變生成。
- 第 2 階段*就是*等價突變體過濾。
- 第 3 階段用**「殺死突變體」**作為每個生成測試的接受／拒絕判準。

LLM 提供*流暢度*（寫出地道的測試程式碼）；突變測試提供*基準真相*（它真的有用嗎）。兩者單獨都不夠。

---

## 招牌成果

在 Meta 的程式庫上，ACH 被套用到數千個類別：

- 生成瞄準特定錯誤類型（如隱私合規回歸）的測試。
- **多數生成的測試在審查中被工程師接受**。
- 致勝點在於*方向*：測試瞄準真實的錯誤類別、每一個都被驗證能殺死一個突變體 —— 而非為覆蓋率而覆蓋率。

（覆蓋導向 vs 缺陷導向的對比見 #36。）

## 工具演示

在 `/section-advanced` 開啟 **LLM 管線探索器**：

1. 對一個範例目標，逐步走過階段 1 → 2 → 3。
2. 在第 2 階段，看等價突變體被濾掉。
3. 在第 3 階段，看一個生成的測試對原程式與突變體各跑一次。
4. 注意接受／拒絕的決定是突變殺死檢查 —— 不是人的品味。

## 小結

- 原始 LLM 寫出合理但未驗證的測試 —— 有覆蓋、沒抓錯。
- **ACH** 把 LLM 包進三階段管線：**突變 → 等價過濾 → 測試生成**。
- 第 3 階段有**客觀預言**：留下的測試必須在原程式通過、在突變體失敗。
- LLM 給流暢度；**突變測試給基準真相。**

**課堂練習：** 為什麼第 3 階段能自動接受／拒絕測試，而「叫 LLM 寫測試」不能？
