# 契約測試（Contract Testing）
### 不部署雙方，也能驗證*介面*

軟體測試視覺化系列 #41 · 驗收與 E2E
搭配工具：`/section-acceptance`（[ContractTestingExplorer](../../src/components/ContractTestingExplorer.js)）

<!-- 契約測試是對「E2E 對服務間整合太慢、太脆」這個問題的務實答案。 -->

---

## 為什麼有這一講

- 微服務透過 API 整合。當一個**提供者（provider）**改了 API，每一個**消費者（consumer）**都可能無聲地壞掉。
- 用一個完整 E2E 環境來抓這件事（#40）又慢、又脆、維持成本又高。
- **契約測試**驗證兩個服務之間的*介面約定* —— **無需**把雙方一起部署。
- 它能早、快地，在一次正常的 CI 執行中抓出破壞性的 API 變更。

---

## 消費者與提供者

| 角色 | 意義 |
| --- | --- |
| **消費者（Consumer）** | *呼叫* API 的服務 |
| **提供者（Provider）** | *實作* API 的服務 |
| **契約（Contract）** | 消費者對提供者回應的、被記錄下來的期望 |

消費者說：*「當我呼叫 `GET /orders/42`，我預期得到一個含 `id`、`total`、`status` 的 JSON 物件。」* 那份被記錄下來的期望，**就是**契約。

---

## 消費者驅動契約

定義性的觀念：**消費者**從它*實際使用的東西*寫出契約。

```
 消費者測試  ──記錄──▶  契約  ──驗證對照──▶  提供者
   「我需要 id、                                「我還回傳
    total、status」                              那些嗎？」
```

- 契約只擷取消費者**依賴的**欄位 —— 不是整個 API。
- 提供者在*自己的* CI 裡，把契約拿來對自己驗證。
- 雙方都不需要對方部署 —— 各自對著**契約**測試。

---

## 什麼算破壞性變更

提供者的 CI 重播契約，把真實回應與消費者的期望做差異比對：

| 變更 | 破壞性？ |
| --- | --- |
| 移除一個消費者會讀的欄位 | **是** |
| 重新命名一個欄位 | **是** |
| 改變一個欄位的型別（`number` → `string`） | **是** |
| 把一個必填欄位變成選填／可為 null | **是** |
| **新增**一個消費者忽略的欄位 | 否 |

> 規則：**別拿走 —— 或改變 —— 消費者依賴的東西。** 新增是安全的。

---

## 契約測試的定位

它填補了兩個都不令人滿意的選項之間的缺口：

- **用 mock API 的單元測試** —— 快，但 mock 可能與真實提供者*漂移*。你測的是一個虛構。
- **完整 E2E**（#40）—— 真實，但慢又脆。
- **契約測試** —— 像單元測試一樣快，而契約是*對著真實提供者驗證過的*。mock 不再會漂移。

它是每次提交都跑的整合安全網。

---

## 工具演示

在 `/section-acceptance` 開啟**契約測試探索器**：

1. 讀一個情境：消費者的期望 vs 提供者的實際回應。
2. 看結構差異 —— 哪些欄位相符、哪些不同。
3. 看一個破壞性變更（移除／重新命名／改型別的欄位）被標記出來。
4. 加一個新欄位，確認它**不是**破壞性的。

---

## 小結

- **契約測試**驗證**消費者**與**提供者**之間的介面約定 —— 無需部署雙方。
- **消費者驅動**：消費者只記錄它依賴的欄位；提供者驗證自己仍遵守它們。
- **破壞性** ＝ 移除／重新命名／改型別／弱化一個被依賴的欄位；**新增**是安全的。
- 它是 mock 單元測試與完整 E2E 之間，那個又快又不易碎的中間地帶。

**課堂練習：** 一個提供者把 `total` 改名為 `amount`。某消費者讀 `total`。破壞性嗎？若提供者兩個都保留呢？
