# 用例測試衍生
### 穿過用例的每一條流程都是一個測試

軟體測試視覺化系列 #39 · 驗收與 E2E
搭配工具：`/section-acceptance`（[UseCaseDerivationExplorer](../../src/components/UseCaseDerivationExplorer.js)）

<!-- 一個用例是整個互動的黑盒規格。這一講是把那段互動轉成測試套件的食譜。 -->

---

## 為什麼有這一講

- 需求常以**用例（use case）**的形式抵達：一段以目標為導向、描述參與者如何與系統互動的敘述。
- 一個用例內容豐富 —— 它描述*快樂路徑*，也描述出錯時會怎樣。
- 穿過它的每一條不同路徑，是一種不同的行為 —— 因此是一個不同的**測試案例**。
- 這一講是那個有系統的食譜：**用例 → 流程 → 測試案例。**

---

## 用例的構造

| 部分 | 意義 |
| --- | --- |
| **參與者（Actor）** | 誰發起這次互動 |
| **目標（Goal）** | 參與者想達成什麼 |
| **前置條件** | 開始之前必須為真的事 |
| **流程（Flows）** | 通往目標 —— 或偏離它 —— 的步驟序列 |

例 —— *ATM 提款*：參與者＝持卡人；目標＝提領現金；前置條件＝卡片已插入。

---

## 三種流程

一個用例包含的不只是快樂路徑：

- **主流程** —— 成功路徑。一切順利。
- **替代流程** —— *仍然成功的其他方式*（如選擇不同的帳戶）。
- **例外流程** —— *失敗的方式*（PIN 錯誤、餘額不足、卡片被吞）。

```
            ┌─ 替代流程 ──┐
 開始 ──▶ 主流程 ──────────┴──▶ 達成目標
            └─ 例外流程 ──▶ 未達成目標
```

一個常見的 bug 來源：團隊測了主流程，卻忘了例外流程。

---

## 衍生規則

> **一條流程 → 一個測試 scenario。**

對每一條流程：

- **設置** ＝ 用例的前置條件，加上任何能把執行導入*這條*流程的東西。
- **步驟** ＝ 該流程的步驟序列。
- **預期結果** ＝ 該流程的結果（達成目標，或那個特定的失敗）。

涵蓋**每一條**流程 —— 主、替代、*與*例外 —— 用例就被完整操練。

---

## 例題：ATM 提款

| 流程 | 種類 | 測試 scenario |
| --- | --- | --- |
| 用有效 PIN、餘額足夠提款 | 主 | 吐鈔、餘額更新 |
| 改從儲蓄帳戶而非支票帳戶提款 | 替代 | 從所選帳戶吐鈔 |
| 輸入錯誤的 PIN | 例外 | 拒絕存取、提供重試 |
| 餘額不足 | 例外 | 交易被拒、不吐鈔 |
| 三次 PIN 錯誤 | 例外 | 卡片被吞 |

一個用例 → 五個測試 scenario —— 而例外流程佔了*大多數*。

---

## 用例與 BDD

用例流程能乾淨地對應到 Gherkin（#38）：

- 每條**流程**變成一個 **Scenario**。
- 前置條件 → **Given**；觸發步驟 → **When**；結果 → **Then**。

所以用例衍生是*分析*步驟；BDD／Gherkin 是把產生的 scenario 寫下來的一種*記法*。它們互補，不互斥。

## 小結

- 一個**用例**描述以目標為導向的互動 —— 參與者、目標、前置條件、流程。
- 它有**主**、**替代**、**例外**流程；例外最容易被忘記。
- 衍生規則：**一條流程 → 一個測試 scenario** —— 涵蓋每一條。
- 用例衍生是分析；**BDD／Gherkin** 是寫下 scenario 的一種方式。

**課堂練習：** 為「登入一個 Web 應用」寫出主流程、一條替代流程、兩條例外流程。那是幾個測試案例？
