# 測試替身（Test Doubles）
### 替相依站位的替身

軟體測試視覺化系列 #27
搭配工具：`/section-blackbox`（[TestDoublesExplorer](../../src/components/TestDoublesExplorer.js)）

<!-- 這一講的任務：用五個精確的詞，取代學生對什麼都用的那個含糊字「mock」。 -->

---

## 為什麼有這一講

- 一個單元很少獨自運行：它會呼叫資料庫、付款 API、時鐘。
- 單元測試必須**快速、決定性、隔離** —— 它不能等一個真實的資料庫。
- 一個**測試替身**在測試期間替真實相依站位。
- 「mock」被鬆散地用來指*全部*替身 —— 這一講給你五個精確的名字。

---

## 問題：一個單元與它的協作者

```
        ┌──────────────┐
        │   受測單元   │──▶ 付款 API    （慢、真的錢）
        │              │──▶ 資料庫      （慢、共享狀態）
        └──────────────┘──▶ 系統時鐘    （非決定性）
```

測那個單元，不是測它的協作者。把每個協作者換成一個你能掌控的**替身**。

---

## 五種測試替身（Meszaros）

| 替身 | 它做什麼 | 用於 |
| --- | --- | --- |
| **Dummy** | 被傳入但從不被用 —— 填一個參數位 | 滿足函式簽章 |
| **Stub** | 對呼叫回傳預先準備好的答案 | 掌控進入單元的*輸入* |
| **Spy** | 一個會額外**記錄**自己如何被呼叫的 stub | *事後*檢查呼叫 |
| **Mock** | 預先設定**期望**；不滿足就讓測試失敗 | *當下*斷言互動 |
| **Fake** | 一個真能運作、但簡化的實作 | 輕量替身（如記憶體內 DB） |

它們構成一個能力與耦合遞增的階梯。

---

## 狀態驗證 vs 行為驗證

五種替身分成兩種測試風格：

- **狀態驗證** —— 跑完單元，然後**檢查產生的狀態／回傳值**。用 **dummy、stub、fake**。
- **行為驗證** —— 斷言單元對它的協作者**做了正確的呼叫**。用 **spy 與 mock**。

> *「它產生了正確的答案嗎？」* 對上 *「它和協作者溝通得正確嗎？」*

---

## 例題：一個訂單服務

`placeOrder()` 驗證購物車、扣款、儲存訂單。

| 協作者 | 替身 | 為什麼 |
| --- | --- | --- |
| 記錄器 | **Dummy** | 建構子需要它，與測試無關 |
| 定價服務 | **Stub** | 回傳固定總額，讓測試有決定性 |
| 付款閘道 | **Mock** | *斷言* `charge(total)` 恰好被呼叫一次 |
| 訂單儲存庫 | **Fake** | 一個記憶體內儲存 —— 驗證訂單已被存下 |

一個單元、四個替身 —— 各依測試需要掌控或檢查的東西來選。

---

## 過度 mock 的陷阱

替身越多**並非**越好：

- 一個全靠 mock 接起來的測試，測的是**接線**，不是**行為**。
- 這種測試在每次重構時都壞掉，即使行為沒變 —— 是**易碎**的測試。
- 偏好 **stub/fake ＋ 狀態驗證**；把 **mock** 留給那些互動本身*就是*需求的情形（例如「付款必須恰好扣一次」）。

只 mock **重要的邊界**，不是每一個協作者。

## 工具演示

在 `/section-blackbox` 開啟**測試替身探索器**：

1. 逐一走過 `dummy`、`stub`、`spy`、`mock`、`fake` —— 每個都有程式碼例子。
2. 對每一個，看它替換了什麼、測試接著檢查什麼。
3. 對比 **stub**（掌控輸入）與 **mock**（斷言呼叫）。
4. 注意哪些替身支援狀態驗證、哪些支援行為驗證。

---

## 小結

- **測試替身**替換真實相依，讓單元測試維持快速、隔離、決定性。
- 五個精確詞：**dummy · stub · spy · mock · fake** ——「mock」不是它們全部的同義詞。
- **stub/fake** 驅動*狀態*驗證；**spy/mock** 驅動*行為*驗證。
- 避免過度 mock —— 太多 mock 造成易碎測試，驗證的是接線而非行為。
