# 缺陷的延遲成本
### 為什麼「何時」找到 bug 比「如何」找到更重要

軟體測試視覺化系列 #14
搭配工具：`/section-flow`（[DefectCostExplorer](../../src/components/DefectCostExplorer.js)）

<!-- 這是一講短而具動機性的課。它替整個系列其他課程提供正當理由：及早測試不是偏好，而是經濟學論證。 -->

---

## 為什麼有這一講

- 初學者會問：*「為什麼要早測？最後一次測完不就好了？」*
- 答案是經濟性的，不是風格性的。
- 缺陷不是固定售價的商品 —— **它的價格取決於你何時抓到它。**
- 這一講給你那條曲線：所有測試策略都是為了把它扳彎而存在的。

> 觀念支點：缺陷是一筆**會生利息的負債**。

---

## 成本攀升曲線

修正一個缺陷的相對成本，依它**被發現的階段**而定：

| 發現階段 | 相對成本 |
| --- | --- |
| 需求 | 1× |
| 設計 | 3× |
| 編碼 | 10× |
| 測試 | 40× |
| 上線後 | 100× |

確切數字因研究而異（Boehm 1981；NIST 2002）—— 但**形狀**不變：每往後一個階段，成本約上升一個數量級。

<!-- 強調數字是示意且取整的。可辯護的論點是「數量級的形狀」，而非「恰好 100 倍」。 -->

---

## 成本為什麼會攀升？

一個早期引入、卻晚期才被發現的缺陷，已經有時間**擴散**：

- 一條錯誤的需求被設計者、程式設計師、測試者各自讀過。
- 每一個建立在它之上的下游產出，現在也都是錯的。
- 修正它，意味著要拆解**每一個**依賴它的產出。

```
錯誤的需求
   └─ 錯誤的設計
        └─ 錯誤的程式碼
             └─ 錯誤的測試  ← 全部都要重做
```

缺陷本身沒有變嚴重 —— **是它的波及範圍變大了。**

---

## 例題：一條被誤解的需求

需求寫著「使用者可以重試登入」；團隊假設是*無限次*重試。

| 在何處發現 | 代價是什麼 |
| --- | --- |
| 需求審查 | 一小時 —— 改一句話（**1×**） |
| 設計審查 | 重新設計鎖定狀態（**3×**） |
| 單元測試 | 重寫驗證模組與它的測試（**10×**） |
| 系統測試 | 修正、整輪重測、更新文件（**40×**） |
| 上線後 | 資安事故、緊急修補、稽核、道歉（**100×**） |

同一個缺陷。唯一的變數是**它被抓到的日期。**

---

## 這條曲線隱含的策略：shift left（左移）

若成本隨階段上升，就把每一項偵測活動**盡量往前推**：

- 在設計開始*之前*審查需求。
- 單元測試*與*程式碼一起寫，而非寫完才補。
- 每次提交都跑靜態分析。
- *在精煉故事的同時*就測驗收條件。

「Shift left」不過是**對成本曲線採取行動**。它不是流程流行語 —— 它是算術。

---

## 各階段對應的偵測技術

每個階段都有能廉價抓出該階段缺陷的技術：

| 階段 | 用什麼抓 |
| --- | --- |
| 需求 | 需求審查、原型驗證、範例映射 |
| 設計 | 設計審查、架構走查 |
| 編碼 | 程式碼審查、靜態分析、單元測試 |
| 測試 | 整合／系統／迴歸測試 |
| 上線後 | 監控、事故應變、緊急修補 |

目標：把偵測**往這張表的上方移**。

## 工具演示

在 `/section-flow` 開啟**缺陷成本探索器**：

1. 看五根階段長條 —— 注意高度是**對數**刻度。
2. 點任一階段，看它的例子與該階段抓缺陷的技術。
3. 比較需求長條（1×）與上線後長條（100×）。
4. 沿著階段往下追一個缺陷，看著倍數變大。

探索器讓這條曲線變得具體 —— 整門課正是圍繞這條曲線編排的。

## 一個持平的但書

- 「100×」這個數字是**示意性的**，來自較早期的瀑布式研究。
- 現代持續交付縮短了各階段 —— 但*形狀*仍然成立：一次上線事故，仍遠貴於一句審查意見。
- 教訓是方向性的：**越早越便宜**，而非「恰好 100 倍」。

## 小結

- 缺陷的成本取決於**何時被發現**，而非它是什麼。
- 成本每階段約上升 10×，因為缺陷會**擴散**進下游工作。
- 「Shift left」就是對那條曲線採取行動 —— 在便宜的早期就偵測。
- 本系列後續每一講，都是一種*左移的技術*。

**課堂練習：** 拿一個你的團隊近期出貨的 bug。哪個階段引入了它？哪個階段*本來可以*抓到它？估算成本差距。
