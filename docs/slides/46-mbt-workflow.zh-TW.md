# 模型驅動測試工作流程
### 把測試設計視為*模型推導*

## 為什麼有這一講

- 狀態遷移測試（#22）已暗示過：一個*模型*可以作為測試基礎。
- **模型驅動測試（MBT）**把它系統化 —— 建一個抽象模型，再從它自動*生成*測試。
- 測試設計不再臨時拼湊，而成為**模型推導**。
- 這一講是地圖：本系列其餘部分將細講的六階段 MBT 管線。

---

## 六階段管線

```
 模型 ─▶ 準則 ─▶ 抽象 ─▶ 具體化 ─▶ 執行 ─▶ 判定
                測試
```

| 階段 | 它產出什麼 |
| --- | --- |
| **模型** | 一個精確的行為模型（通常是 FSM） |
| **準則** | 一個覆蓋目標 → 一組測試義務 |
| **抽象測試** | 滿足準則的模型層級事件序列 |
| **具體化** | 具體的 API 呼叫 ＋ 真實輸入值 |
| **執行** | 對真實系統執行具體測試 |
| **判定** | 比對觀察行為 vs 模型的預測 |

---

## 階段一 —— 模型

模型是預期行為的**精確、抽象**描述 —— 通常是一台有限狀態機。

- 它是**單一真實來源**：後續每個階段都從它讀取。
- 錯誤的模型產生錯誤的測試 —— *垃圾進、垃圾出*。
- 它必須夠抽象以可處理，又夠詳細以暴露你在意的缺陷。

---

## 階段二～三 —— 準則與抽象測試

**準則** —— 要多徹底地操練模型：所有狀態、所有轉移、轉移對、來回路徑。準則展開成一組具體的**測試義務**。

**抽象測試** —— 走訪模型以履行每個義務。結果是一組模型詞彙層級的**事件序列**：

```
 抽象測試：  validCard · push · timeout
```

還沒有真實的值 —— 只有測試的*形狀*。

---

## 階段四～五 —— 具體化與執行

**具體化** —— 把每個抽象事件對應到具體動作與真實資料：

```
 validCard  ──▶  reader.swipe("EMP-4417")
 push       ──▶  door.push()
 timeout    ──▶  clock.advance(5000)
```

模型的詞彙在此與真實的受測系統（SUT）接軌。

**執行** —— 對 SUT 執行具體測試，記錄每一步觀察到的狀態／輸出。

---

## 階段六 —— 判定

把 SUT *做了什麼*與模型*預測了什麼*比對：

- **相符** → 測試**通過** —— SUT 符合模型。
- **分歧** → 測試**失敗** —— 而失敗的那一步定位出缺陷。

失敗代表模型與系統**意見不合**。缺陷在兩者之一 —— 要嘛 SUT 錯了，要嘛模型已不再反映現實。

---

## 離線 vs 線上 MBT

跑這條管線的兩種方式：

| | 離線 MBT | 線上 MBT |
| --- | --- | --- |
| 生成 | 整套事先生成 | 下一步即時決定 |
| 產出 | 可重用、可檢視的套件 | 沒有儲存的套件 —— 即時調適 |
| 適合 | 決定性系統、回歸 | 非決定性／長時間運行的系統 |

離線給你產物；線上處理不可預測性。

## 小結

- **模型驅動測試**從一個明確的模型生成測試 —— 測試設計成為模型推導。
- 六階段：**模型 → 準則 → 抽象測試 → 具體化 → 執行 → 判定**。
- **模型**是單一真實來源；一次**判定**失敗代表模型與系統不一致。
- **離線** MBT 產出可重用套件；**線上** MBT 調適於非決定性。

**課堂練習：** 為一個旋轉門畫一台 3 狀態的 FSM。挑一個準則。其中一條抽象測試是什麼，你會如何具體化它？
